# Miftāḥ: full review, November 2026

This review covers every domain:
- build and repo;
- code architecture;
- performance;
- layout on every screen size;
- UI/UX, screen by screen;
- accessibility;
- security and privacy;
- learning content;
- Arabic.

Every number below was measured on the shipped bundle (`build/assets/www`), not the dev files. Timings are at **4× CPU slowdown**, roughly a mid-range Android phone.

The work is ordered as a plan. **Phase 0** must be done before the repo goes public. **Phase 1** is what users will feel most. **Phase 2** makes it excellent. Each item says what is wrong, the evidence, what to do, and roughly how big the job is (S: hours, M: a day or two, L: several days).

---

## Verdict

Miftāḥ is unusually honest and well tested for an app of its kind:
- Every worked maths and science line is checked by calculation on every build.
- Exams can't be gamed.
- It runs fast once loaded, and keeps a 29 MB heap.

Its weaknesses are mostly visible to contributors and tablet users rather than children on phones:
- **The code is hard to read for newcomers.** Curriculum files are layered by history, many views wrap other views, and lines run very long.
- **Tablets and landscape phones get a stretched phone layout.** One case is a real bug: in landscape the lesson keypad sits below the screen.
- **The repo isn't ready to publish.** The signing key and password sit in the project folder, there is no `.gitignore` or licence, and the README is out of date.
- **Depth is uneven.** 18% of lessons are taught in full, and the youngest and oldest years have none.

| Domain | Today | After Phase 0–1 |
|---|---|---|
| Build and repo hygiene | Not publishable | Publishable |
| Code clarity for contributors | Hard | Fair |
| Performance on a mid-range phone | Good after start; slow first start | Good |
| Layout: phones (portrait) | Good | Very good |
| Layout: tablets and landscape | Stretched; one blocking bug | Designed |
| Accessibility | Dark theme passes; light fails in places; drag activities have no alternative | Passes WCAG AA for text |
| Security and privacy | Mostly careful; three real gaps | Solid |
| Learning depth | 18% taught in full | Rising year by year |

## Phase 0: before the repository goes public

### 0.1 Take the signing key out of the project (S, critical)
- **Problem:** `keystore/miftah-release.jks` and `keystore/keystore.properties` sit inside the project, and the password is in plain text. If they're published, anyone can sign an "update" to Miftāḥ.
- **Do:**
  - Move both files outside the repo, for example `%USERPROFILE%\.keys\miftah\`.
  - Have `build.sh` read `MIFTAH_KS`, `MIFTAH_KS_PASS` and `MIFTAH_KEY_ALIAS` from the environment, and fail with a clear message if they're missing.
  - Back up the key twice, offline. Losing it means never updating the Play listing again.

### 0.2 Add a `.gitignore` (S)
Exclude:
- `build/`, `dist/`
- `tools/src/` (378 MB), `tools/.node/`, `tools/.bin/`
- `keystore/`, `*.jks`, `*.properties`
- `art-inbox/` (raw art)
- `build/e2e/`, and any scratch screenshots

Then check the size of a fresh clone. Target under 100 MB, most of it audio, images and fonts that ship.

### 0.3 Add licence files (S)
- `LICENSE` for the code (MIT or Apache-2.0).
- `CONTENT.md` listing each content source and its terms. The README's sources table is a good start.
- Keep third-party content in its own folders (`web/audio/h`, the Qur'ān text, translations) so the boundary between code licence and content terms is obvious to forks.

### 0.4 Rewrite the README for strangers (S)
It is out of date:
- it says "children aged 2 to 11" and "about 300 MB";
- it points to files that moved (`web/js/engine.js`, `web/js/_audit.js`).

The new README should cover:
- what the app is (one paragraph and screenshots);
- how to build it on Windows, macOS and Linux;
- how to run the tests;
- where things live (link `ARCHITECTURE.md`);
- how to add a lesson;
- the content rules (verified sources only, no faces, the Qur'ān never gamified);
- how to contribute.

### 0.5 Tidy the planning documents (S)
- Move `AGE-UX.md`, `ENGINE.md`, `PLAN-12-18.md`, `V2-PLAN.md`, `brief.md`, `CURRICULUM.md`, `AUDIT.md` and this file into `docs/`. Each gets one line at the top saying whether it is current or historical.
- Move `desktop/` (on hold) to `experimental/`, or leave it out of the first public commit.

### 0.6 Make the build reproducible on any machine (M)
- `build.sh` assumes `$LOCALAPPDATA` and Windows `.exe` tools. Detect the OS, or read `ANDROID_HOME` only.
- Pin tool versions in a small `package.json`: esbuild exact version, and `npm ci` to install it.
- One source of truth for the version: the manifest says `versionCode 1` while `build.sh` says `VCODE=2`. Put the version in one file (`version.txt`) and have both read it.
- Add `CHANGELOG.md`; the README's changelog stops at 1.0.

### 0.7 Run the tests on every push (S)
Add a GitHub Actions workflow that runs:
- `node tools/test.js`, `smoke.js`, `teach-check.js` and `strings.js`;
- the bundle step.

The headless-browser checks (`teach-screens`, `e2e-honesty`) can run on a schedule. They are the project's best protection and should be visible to every contributor.

## Phase 1: what users feel most

### 1.1 Landscape phones: the lesson keypad is off screen (S, blocking)
- **Evidence:** at 844×390, the keypad's top is at 298 px on a 390 px screen. It sits inside a scrolling area with nothing on screen showing that it's there. A child holding the phone sideways sees the question and a "?" but no keys.
- **Do:** below 500 px of height, lay a lesson step out in two columns, with the question, diagram and working on the left and the keypad or choices on the right. Use one container query on `.pl-body`, not per-instrument CSS.

### 1.2 Make the first start fast (M)
- **Evidence:** a 758 ms freeze on first start, and 5 MB of script parsed up front, including the 2.2 MB `quran-rest.js` that most screens never need.
- **Do, in order:**
  1. Load `quran-rest.js` only when a Qur'ān or memorisation screen first opens. Keep a small "loading the muṣḥaf" state.
  2. Split the curriculum by stage. A 6-year-old's device never needs Year 12 chemistry at start. Load each stage's files the first time that stage's room or year opens, and keep the lesson index (ids, titles, units) in the main bundle so planning still works.
  3. Paint the welcome or home shell before the curriculum finishes evaluating. The door animation hides the rest.
- **Target:** under 1 s to first paint and no task over 200 ms on a cold start at 4×.

### 1.3 Tablets and wide screens: design them (M–L)
Today every screen is the phone layout, centred or stretched. At 800×1280:
- the home screens use the top half and leave the rest empty;
- the lesson is a narrow column in a sea of space;
- the subject path is a thin line down the middle.

Screen by screen:

| Screen | Tablet portrait (≥ 700 px wide) | Tablet landscape and desktop (≥ 1000 px) |
|---|---|---|
| Child home | Hero 40% of the height; "Today's path" as a 2-column grid of larger cards | Two panes: hero and next step on the left, path and week on the right, full height |
| Teen home | Add a right column: this week's minutes chart, next exam, Qur'ān progress, due reviews | Three columns: today, week, subjects |
| Lesson player | Scale type and keys to 1.2× (keys 72 px, maths 30–34 px); diagram max 520 px | Question and diagram on the left, answer area on the right, as in 1.1 |
| Subject room (path) | Wider zigzag path with lesson names beside each stop | Path on the left; the selected unit's lessons and progress on the right |
| Rooms grid | 3 columns, already fine; add a small progress ring on each door | 4–5 columns |
| Parent Family page | 2-column child cards | Master–detail: children on the left, the selected child's dashboard on the right |
| Parent child dashboard | 2-column cards | 3-column cards, charts larger |
| Sheets (Look back, group, settings) | Centred dialog of 560 px instead of a full-width bottom sheet | The same |

Use CSS container queries and two or three layout tokens (`--col`, `--gutter`, `--scale`), not separate stylesheets.

### 1.4 Light theme contrast (S)
- **Evidence:** bottom navigation labels measure 2.8:1, and small secondary text (`small`, `.pmin`) 3.5:1. The minimum is 4.5:1. Dark theme passes everywhere.
- **Do:** darken the light theme's `--t2` and `--t3` tokens until both pass, and give inactive navigation labels `--t2`. Add the contrast probe (from this review) to `tools/` so a future colour change can't regress it.

### 1.5 The Android bridge is visible to embedded videos (M, security)
- **Problem:** `addJavascriptInterface` exposes `AndroidBridge` to every frame in the WebView, including the YouTube iframe used for parent-added videos. Third-party script in that frame could call `openUrl`, `shareFamily` or `exportFamily`.
- **Do, either:**
  - play videos in a separate activity whose WebView has no bridge (simplest, and also contains autoplay and suggestions); or
  - replace `addJavascriptInterface` with `WebViewCompat.addWebMessageListener` and an origin allowlist of `https://appassets…` only.

### 1.6 The parent PIN is stored and compared as plain text (S)
- **Problem:** `A.S.pin` is compared with `===` and travels inside the family file shared over WhatsApp or Bluetooth.
- **Do:** store a salted hash (PBKDF2 through `crypto.subtle`, 100k rounds), compare hashes, and keep the hash in the family file so the PIN still works on the other device.
- Add a recovery route: answer a long sum and confirm on the device by holding a button for 5 seconds. A forgotten PIN today locks a parent out for good.

### 1.7 The manifest contradicts itself about the internet (S)
- **Problem:** a comment says "no INTERNET: nothing can leave the phone", while the next line requests `android.permission.INTERNET`. It is only needed for parent-added YouTube videos and simulations.
- **Do:**
  - Fix the comment to say exactly that.
  - Consider shipping a build flavour with the permission removed and videos switched off, for families who want a guaranteed offline device.
  - Add the guarantee to the store listing.

### 1.8 Decide what Android backs up (S)
- **Problem:** `allowBackup="true"` with no rules sends the whole app's data, including recordings of children's voices, to the user's Google backup.
- **Do:** add `dataExtractionRules`. Keep learning progress and the PIN hash (useful when a phone is replaced); leave recordings out unless a parent opts in.

### 1.9 Saving after a long year (M)
- **Evidence:** after a simulated year the state is 730 KB, and every save stringifies all of it (29 ms at 4×). A three-child family after two years could reach several MB per save, which stutters on low-end phones.
- **Do:**
  - Debounce saves to once per 2 s of quiet and on `pagehide`.
  - Move the event ledger to an append-only native file (or IndexedDB), with a snapshot every 1,000 events.
  - Keep `A.S` for settings and projections only.

### 1.10 Lift the text-size cap (S)
- **Problem:** `setTextZoom` caps system text at 125%. The layout passes at 125%; children and parents with low vision use 150–200%.
- **Do:** allow up to 200%, then run the layout audit at 150% and 200% and fix what breaks. Most screens already use `clamp()`.

## Phase 1 continued: UI/UX upgrades, screen by screen

These go beyond fixes. Each is small and specific.

### Everywhere
1. **Screen transitions:**
   - Use the View Transitions API, which Android's Chromium WebView supports: a shared-element morph from a path card into the lesson header, and from a door into its room.
   - Keep the door for the first lesson of the day only, and a 180 ms cross-fade elsewhere.
   - Respect reduced motion: fades only.
2. **One type scale.** Define `--fs-xs` to `--fs-3xl` with `clamp()`, and replace the many fixed sizes in CSS and inline styles. Most inconsistencies seen in the screenshots come from one-off sizes.
3. **One spacing scale and one radius scale**, for the same reason; 306 inline styles in JS make this hard today (see 2.3).
4. **Pressed states:** every tappable card gets a 0.98 scale and a deeper shadow on press, with one haptic tick. Some controls already do; make it universal.
5. **Feedback:**
   - **Right answer:** a soft chime, a gold glow on the answer slot and the key bar filling.
   - **Wrong answer:** a gentle 6 px shake and the misconception note sliding up from the bottom (not appearing in place), so the eye knows where to look.
6. **Skeletons, not blank screens:** while a room's curriculum file loads (after 1.2), show the path's shape in grey.
7. **Empty states with a next action.** Cards, Keys, Group and Exams each get a small illustration and one button that does the obvious thing. Some already do; standardise them.

### Child home (ages 2–11)
- **Hero size:** on short phones (below 700 px tall) cap the hero at 32% of the screen, so "Today's path" starts above the fold.
- **Path rows:** a coloured progress dot and a state (next, done, saved for later) without needing to read; the current item gently glows.
- **After the last stop:** a calm "done for today" card, with what was learned (keys shown) and a suggestion to go outside, instead of an empty list.

### Teen home (12–18)
- The Start card added in the UI pass works. Add a **week strip**: seven small bars of minutes, with today highlighted, under the greeting.
- Show due reviews as a number with a one-tap "do them now (about 6 min)".

### Lesson player
1. **Landscape and tablet layout:** see 1.1 and 1.3.
2. **A visible plan for the session:** the key bar shows segments; label the current phase (Learn, Watch, Together, Your turn) above it in small caps. It exists as a tag; tie it to the bar.
3. **Keypad:**
   - Keys 64 px on phones, 72 px on tablets.
   - The answer slot grows to fit long answers.
   - A long-press on Delete clears.
   - The fraction key shows a stacked preview while typing.
4. **Watch steps:** a small "1 of 3" counter beside "Next step", so the child knows how much working is coming.
5. **After three misses:** the revealed working gets a "Try one like it" button that generates a fresh question of the same kind before moving on. This turns failure into practice.
6. **End of lesson:**
   - **Younger children:** the key forging animation with the score in words ("You did 4 on your own").
   - **Teens:** the new result card (score, key, what's next) is right; add the time taken.

### Subject room
- A **sticky year tab bar** that snaps to the current year.
- A "**jump to next**" chip, so a child deep in a long path returns to their place.
- **Locked stops** show why ("after The 2 times table") on tap, instead of nothing.

### Keys page
- The new per-subject rows read well. Add the three key counts as a small **ring chart** above, and tapping a subject jumps to its room.

### Parent Family page
- Each child card shows a **7-day sparkline** of minutes and one "needs you" line in the parent's language ("2 answers to check", "stuck on fractions"), with a single action.
- **Tablet:** master–detail (1.3).

### Parent child dashboard
- A **misconceptions panel:** taught lessons already know which wrong answer means which mistake. Count them per child per week and show the top three in plain words ("adds the bottoms of fractions"). This is high-value and nearly free; see Phase 2.

### Welcome and setup
- After adding the first child, show a **15-second tour**: three cards with a picture each (what the child sees, what the parent sees, how to share between devices). Skippable, shown once.

## Phase 2: code that contributors can work in

### 2.1 One way to define a lesson (L)
- **Problem:** lessons are defined through `C.add`, `C.les`, `C.topic`, `C.study`, `C.yunit` and `C.teach`, across 54 files layered by history (`cur-math`, `cur-math2`, `cur-deep-math`, `cur-a-math`, `cur-sr-math`, `cur-tm-y5`…). Later files patch earlier ones through `C.deep`. A contributor can't find "the Year 5 fractions lesson" without searching.
- **Do:**
  - Reorganise into `curriculum/<subject>/y05.js`: every lesson for that subject and year in one place, in one style. Taught lessons (`teach`) and short lessons sit side by side.
  - Write a one-off codemod that runs the current files, walks `C.skills`, and emits the new files in a single schema. The tests prove nothing changed.
  - Document the schema in `docs/LESSONS.md` with one example per step kind.

### 2.2 Replace view-wrapping with hooks (M)
- **Problem:** `A.V.home` is wrapped by three files, and `__native.onImport` by three. Behaviour depends on script order, which the bundle hides.
- **Do:** give the router named slots (`A.view('home', render)`, `A.on('home:after', fn)`) and a small event bus for native events (`A.native.on('import', fn)` with an explicit handled flag). Then remove every `var x0 = A.V.x; A.V.x = …` chain.

### 2.3 Templates that escape by default (M)
- **Problem:** views build HTML with string concatenation and `esc()` by hand (132 `innerHTML`, 306 inline styles). One forgotten `esc()` is an injection bug: child names and challenge data are user-controlled.
- **Do:**
  - Add a 40-line tagged template, ``html`<b>${name}</b>` ``, that escapes every value unless it is wrapped `raw()`.
  - Move inline styles into classes as each view is touched.
  - Do it view by view; no big-bang rewrite.

### 2.4 Formatting and linting (S, then ongoing)
- **Problem:** 1,696 lines are over 500 characters. Diffs on such lines are unreadable in review, which matters most once strangers send pull requests.
- **Do:**
  - Add Prettier (`printWidth: 120`) and ESLint (recommended rules, `no-undef` with the known globals declared).
  - Run Prettier once over `core`, `lesson`, `instruments` and `views` in a single "format only" commit.
  - Leave generated data (`data/gen.js`) unformatted.
  - Add `.editorconfig`.

### 2.5 Modules instead of globals (L, later)
- **Problem:** 96 files share globals (`A`, `C`, `I`, `M`, `Player`, `Teach`, `Dia`…) and depend on script order.
- **Do:** move to ES modules with esbuild bundling, one folder at a time, starting with `lesson/` and `instruments/`. This is what lets 1.2 (load by stage) stay clean rather than becoming another order hack.

### 2.6 Test layout (S)
- Move `tools/*.js` checks into `tests/`, keep build tooling in `tools/`, and add `npm test` and `npm run e2e` scripts.
- Turn this review's probes (performance, layout by size, contrast) into `tests/e2e/` so they run on a schedule and fail when a number regresses.

**Order of work:**
1. **English reading, Years 1–4.** Phonics and early reading carry everything else. They need real recorded phonemes (121 word recordings exist, and the device voice is approximate for sounds).
2. **Maths, Years 1–4,** on the same engine. It is ready, and the checker covers it.
3. **Arabic, Years 1–6:** reading with harakāt, then grammar. The word-choice "Together" step built for science suits grammar well.
4. **Maths and science, Years 11–12** (IGCSE): past-paper style questions with mark-scheme style working.
5. **Computing:** a small in-app code runner for Python-style pseudocode would turn 97 short lessons into practice.

**Two systems that would lift every subject:**
- **A written-work loop:** the child photographs work, and the parent marks it against a 3–5 point checklist on screen. It counts as evidence.
- **Recorded explanations:** the child records "explain it back" in 30 seconds; the parent listens and marks it heard. Teaching it back is among the strongest ways to learn.

## What I would do differently if building it from scratch, and some fresh ideas

1. **Data first, screens second.** Every lesson would be a typed data object (one schema, validated at build), and every screen a small function of state. The current code reached the same place by layering, which is why 2.1 and 2.2 exist.
2. **Misconception insight for parents.** The taught lessons already know which wrong answer means which misunderstanding. Collect those tags per child and show parents a weekly plain-language list with one suggested 5-minute activity each. No other homeschool app does this well, and Miftāḥ has the data already.
3. **Two-device co-teaching.** The child uses a tablet while the parent's phone shows a live script: what the child sees, what to say, the answer, and where they're stuck. It works over the home Wi-Fi with no internet: pair once by QR, then use Android's Nearby Connections. It also makes sharing between devices automatic.
4. **Siblings side by side.** On a tablet in landscape, split the screen for two children, each on their own path. Families with several children share one tablet more often than not.
5. **"Try one like it"** after any miss (see the lesson player). Generators make this free and it is the single best follow-up to an error.
6. **Prayer-aware days.** The app already knows the Hijri date. Let parents enter their prayer times (or approximate them by city, offline). Lessons then pause gently at the adhān and resume after, and the day's plan bends around ṣalāh instead of the other way round.
7. **A community lesson pipeline.** Once open source, accept new taught lessons through pull requests. The gate is that `teach-check` computes every line and `teach-screens` renders it in both languages. Contributors get instant, objective feedback, and quality holds as the curriculum grows.
8. **Printable weekly workbook.** Build a 4-page PDF each week from the child's own misses, with the working on the back page. Offline families use paper as much as screens.
9. **Accessibility modes:**
   - a switch-access mode (large targets, step through choices with one button);
   - a dyslexia-friendly reading font option;
   - tap-to-place alternatives for every drag activity (sort, match, clock, order). Today these have no keyboard or screen-reader path.
